## WARP setup for the operator

Use Cloudflare Zero Trust **Networking > Routes > Create route > Tunnel CIDR** with the existing Abashyaka tunnel and destination **`172.20.0.10/32`**. Do not route the wider Docker subnet; the OTP reader and databases must not become reachable. Configure device enrollment and a network policy permitting only the named testers to access TCP port 8080 on that address. Install and enroll the Cloudflare One Client/WARP on each test phone in Traffic and DNS mode. Adjust Split Tunnels to include that exact `/32`, because private ranges are normally excluded. Check for overlap with existing Cloudflare routes or the phone's local network before adding it. See [Cloudflare's private CIDR instructions](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/private-net/cloudflared/connect-cidr/).

The intended QA APK define is `API_BASE_URL=http://172.20.0.10:8080` with `QA_OTP_AUTOMATION=false`. This HTTP endpoint is solely for an authenticated private WARP test path; it is not an HTTPS/public release endpoint. The debug manifest permits cleartext traffic. Do not use this address or debug build for production distribution. WARP device policy, private route and end-to-end encryption assumptions must be verified on the actual devices; merely installing consumer WARP without enrolling in the correct Zero Trust organization is insufficient.

After the route and enrollment exist, verify from an enrolled phone on mobile data with Wi-Fi off; `http://172.20.0.10:8080/healthz` should respond and the same address should be inaccessible from an unenrolled device. This is not yet tested. No Cloudflare account or route was changed by the agent.

The existing public `api.abashyaka.com` stack uses production-mode authentication and has QA OTP disabled. It must not be repointed to a QA database, reconfigured to reveal OTPs, or used with synthetic QA fixtures. The existing secure helper in `backend/internal/qaotpinbox` supports QA-only delivery: synthetic allowlisted accounts, challenge-scoped, single-use, short-lived reader capabilities, separate writer and runner secrets, and a root-owned private tmpfs inbox. `docs/phases/AUTH_OTP_02_QA_AUTOMATIC_ENTRY_AND_FAST2SMS.md` records historical emulator acceptance; it does not prove outside-network phone support.

## Proposed operator-assisted setup

1. Provision a separately named, isolated QA Compose project with a disposable QA-only PostgreSQL database, API, and existing OTP inbox helper. Keep its database and helper on private networks. No shared/production schema or data changes; no public OTP-reader route. Create only synthetic allowlisted role identities. Keep live SMS, real payments, real cash, payouts and real compensation disabled.
2. Restrict access to a separate QA API hostname or private network for the named test devices. Creating a DNS/published tunnel route requires the user's separate public-exposure approval. Cloudflare browser challenges are not a substitute for a mobile-compatible network access method. Do not expose the private OTP reader, MinIO administration, or database.
3. When a tester requests an OTP for an allowlisted synthetic identity, an authorized operator uses the existing scoped single-use reader through a private connection and supplies the fresh code through a previously agreed secure channel. The tester enters it in the normal app OTP screen. The API never returns the code and logs must not contain it. Challenge ID, phone, purpose, run ID, expiry and runner identity remain bound as in the existing helper.
4. Build a debug QA APK using the isolated QA API URL; never point it at the production API. Before installation, record SHA-256 and current AVD names/serials. Install the same APK on all three role emulators and verify each required synthetic login. Then test on the authorized physical phones via an actual outside network. A Flutter build must run from the user's interactive Windows-host PowerShell using plain `wsl`, as required by `AGENTS.md`; do not automate the terminal via computer use or invoke WSL through the sandbox bridge.
5. Validate Customer, Merchant and Rider UI flows, relevant Admin web, backend authorization and database/ledger reconciliation. Record APK hash, actual emulator mappings, role screenshots, network conditions, test results and limitations. Do not claim full acceptance when any mandatory role is missing.
