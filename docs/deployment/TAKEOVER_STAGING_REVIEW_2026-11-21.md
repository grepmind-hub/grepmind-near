## Critical findings and containment

- The public pre-login registration endpoint could be called without installation authorization and could revoke an existing active installation registration. The FCM OTP implementation used a normal FCM notification body containing the code, contrary to its data-only comment. An additional boolean could enable that provider independently of the `fcm_test` provider guard. Generated installation IDs were predictable, incoming messages were not matched to the active challenge or phone, and missing expiry was treated as valid. These are security defects, not successful acceptance evidence.
- Staging Nginx now denies `/api/v1/devices/register-prelogin` for API and Admin hostnames. The database and original configuration were backed up first. The original is `/opt/abashyaka/secrets/backups/nginx-before-prelogin-guard.conf`. The first reload did not change the live bind-mounted inode; after validating Compose and recreating only Nginx, the external endpoint returned 403 and `https://api.abashyaka.com/healthz` returned 200. Cloudflared and persistent volumes were not recreated. To roll back the guard, restore the original Nginx config to the active host path, validate configuration and recreate only Nginx; restoring the vulnerability should not be done as routine rollback.
- Source changes separately fail closed on pre-login registration and on `FCM_TEST_OTP_ENABLED`, remove OTP notification title/body, use secure randomness for new installation IDs, match OTP messages to the active challenge/phone and expiry, and make the copy action populate the field without submitting. Existing installation IDs are not automatically rotated. Incoming messages that arrive before the challenge response are currently dropped; delivery behavior remains incomplete. These source changes have not been deployed.
- The Android configuration and server credential indicate Firebase project `abashyaka`; the user previously described it as QA-only. The server credential is outside images and mounted read-only, but its file mode is 0644 inside mode-0700 parent directories. The app container runs as UID 100 and can read it. A 0600 mode without a suitable ACL, group, or container secret arrangement would break that access. IAM permissions, OAuth access-token issuance, and actual FCM sends remain unverified. The server Google OAuth value is a placeholder. The intended web client previously supplied by the user is different from the JSON default; no arbitrary substitution was made.
- Google login is incomplete and unsafe to enable: account creation uses the same empty unique phone for all new users, spans non-transactional writes, does not provide explicit authenticated linking, and does not prove preserved role/status behavior. Device registration ownership and lifecycle, FCM retry durability and event coverage, and background delivery also require review. Existing FCM HTTP v1 implementation is lightweight; the original plan asks for Admin SDK while the later takeover instructions explicitly request keeping a correct lightweight implementation rather than adding it for preference. No SDK migration has been made.
